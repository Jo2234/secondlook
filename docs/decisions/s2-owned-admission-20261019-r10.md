## Contract and order

1. The fixture try-on route validates its body. A stored matching request is resolved through the unchanged domain idempotency comparison and returns the stored IDs without a store commit, queue reservation, execution or provider POST. A mismatching body is a conflict. A failed/unknown store fence is checked first; stale memory cannot certify replay after ambiguous persistence. Missing stored jobs return `admission_record_inconsistent`, never replacement work. This is replay of a supplied original request, not a lost-request GET lookup or client POST retry policy.
2. A new request reserves one slot synchronously in `OwnedRuntime` before its admission callback or any admission storage effect. The cap remains 32 batches INCLUDING committing reservations, queued batches and the running batch. N=1 and N=2 both occupy one batch slot; the executor awaits each job, and the runtime awaits each batch. Attempt concurrency remains one. A 33rd reservation refuses before storage; no larger queue or extra worker exists.
3. The serialized store callback rechecks runtime/store/shutdown availability for a new admission and preserves all existing cost, budget, quality, declaration, capability and synthetic-model rights guards. The unchanged domain admission and corresponding jobs, attempts, ledger entries, request record and absolute batch deadline are committed together. A concurrent duplicate found inside the mutex releases its provisional slot and never enqueues another execution.
4. Only after temporary-file write, file fsync, close, rename and directory fsync succeed does the runtime retain a queue/execution promise. The route returns `{mode,jobs}` (200) without awaiting that execution promise. It returns all N IDs in request order. There is no detached `runBatch`, swallowed worker rejection or per-request background worker. Cancellation of the browser response does not cancel durable work; explicit job cancel remains separate. Actual disk/admission latency relative to the UI's 15 s deadline is UNRUN; no finite latency is inferred for filesystem calls.
5. Each reservation retains the admission promise, completion join and controller. Each queued/running batch retains its observed execution promise. Per-attempt controllers remain in Runner, and nested client/native promises remain awaited by the unchanged ownership-preserving `bounded` contract. Normal completion releases capacity. Unexpected commit/queue/execution failures retain a structured sticky runtime fence; freeing a physical slot does not reopen admission. Already-queued batches do not execute after a runtime failure. Their durable commitments remain for quiescent recovery; this does not certify their terminal settlement.

## Storage truth and failure behavior

No state schema, shared type, domain ledger or reducer change is required. `StoreCommitError` is server-local and identifies both commit stage and outcome. Temporary-open/write/sync/close failure is `not_committed` to canonical state; rename-attempt/directory-sync failure is `unknown`. Even a rename rejection is conservatively unknown. Both outcomes fence the store permanently for this owner. The in-memory state is installed only after directory sync. Failed temporary open now participates in the same fence as subsequent write failures.

Only explicit pre-effect route refusals, known store-capacity validation refusal, and the callback's pre-effect `runner_closed` refusal release a provisional slot without creating a runtime failure. All other admission exceptions fence it. Persistence failures are never reclassified as upload/limiter/provider errors. In particular, a failed `limiter_granted`/POST-intent commit cannot yield a request effect, and cannot be turned into `limiter_failed` proof. HTTP exposes store failure/unknown and runtime closed/full/fenced as 503, which carries no promise that a new request is safe. No auto-reset or in-process reconciliation is added.

The existing fsync/close ordering, store bounds, owner-lock create/unlink inventory and fail-closed manual recovery remain. `Store.close` now throws its retained commit failure instead of returning as if close were clean. Before a runtime-failure shutdown reaches `Store.close`, `drain` throws after joining owned work, preserving the lock. No cleanup is evidence that a failed or unknown commit did not happen.

## Deadlines, cancel, recovery and shutdown

The batch deadline is created once from admission time and unchanged `batchDeadlineMs(N, taskDeadlineMs)`. Queue time consumes that deadline. Each queued attempt starts once through the unchanged reducer, which persists its attempt deadline. Existing attempt/task deadlines are never reset on recovery. Each provider call rechecks signal, current state, original attempt/batch bounds and applicable upload/task/download phase bounds after awaited intent storage and immediately inside the bounded call. The original 429-only POST rule, POST count cap, ambiguous-result classification and GET-only restart recovery are unchanged. Durable `postSendStartedAt`, post count and `possibly_spent` commitment still precede the actual task POST.

Startup resumes one previously reconciled task ID at a time through the same runtime and awaits its drain. `resume` refuses queued/unsent or otherwise unsafe attempts; recovery requests are restricted to GET/download. Neither recovery nor replay creates a replacement task POST. One- and two-model batches execute sequentially against the one admission deadline; no per-model renewal is introduced.

Explicit job cancel aborts the active controller before awaiting its durable cancel commit. Queued jobs are durably cancelled and skipped when reached. The response acknowledges durable job state, not provider deletion or proof that all native cleanup has ended. The runtime retains remaining cleanup until drain. Failed cancel persistence fences storage rather than acknowledging success.

Shutdown closes runtime admission first, then aborts owned controllers and the server signal, closes the listener/joins requests, drains reservations and work, disposes the limiter and finally closes storage. The signal-triggered shutdown promise and root server lifetime are retained and joined. A signal during startup arms the same 10 s watchdog. Cancellation-aware operations are joined, never abandoned to meet an artificial promise timeout. If a commit/native operation will not settle, the existing process-level 10 s hard exit remains the bound, with no clean ownership-release claim. No runtime experiment established the watchdog behavior. Owner-unlink/directory-sync failure can make lock release unknown; diagnostics explicitly avoid asserting lock retention on every possible close failure.
