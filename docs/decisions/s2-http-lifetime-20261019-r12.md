## Listener/root lifecycle

Main subscribes to `listening`, `error` and `close` in the same synchronous turn as `serve` returns, also reading `server.listening` to cover readiness already reached. This relies on the Node listener event API; no installed adapter implementation was inspected. Async pre-readiness errors (including EADDRINUSE), later errors and unexpected close synchronously enter the same stop path. Ready is a retained lifecycle milestone, not a release/acceptance signal. An unexpected close before readiness also releases the readiness wait as a failure. The exact first failure value, including null/undefined rejection, is sticky and reaches root rejection/nonzero main outcome.

Stopping before a bind resolves waits for ready/error/close before calling close. Thus NOT_RUNNING cannot be used to excuse a still-pending bind. After that milestone, the production close adapter accepts Node's `ERR_SERVER_NOT_RUNNING` as no running listener, including failed bind; other close callback errors remain failures. Expected closure is marked immediately before invoking close. The close event then proves listener closure without creating an unexpected-close failure, but does not skip waiting for the close callback. Unexpected close is failure even when the Runner has no work.

`stop()` returns the same published promise on every invocation, including reentrant cancel callbacks and simultaneous SIGINT/SIGTERM/error notifications. Its success and failure are observed immediately by a retained observation which wakes the root lifetime; `wait()` then joins that same stop task and propagates rejection. Event handlers start no detached rejecting cleanup promise.

Startup, listener, actual handler and Runner joins use independently observed promises collected by `allSettled`. A failure in one cannot skip another, including synchronous join throws. Every rejected join records its first failure immediately, while all other work stays owned. Limiter disposal follows the joins. Store close occurs only if every join and disposal succeeded and no sticky failure exists. An error never becomes clean merely because request count later reaches zero. A store-close failure retains failure and does not assert whether unlink/directory sync released the lock.

Listener handlers and signal handlers are removed only after all owned joins have settled and the listener is proved closed (or no listener was created). They remain while handler cleanup or Runner work is pending. A rejected close without proof of closure retains listener observers and the original hard watchdog, even if the root can reject after the other joins settle. Once all joins settle and listener closure is proved, the watchdog can be cleared even on a sticky failure which deliberately retains the store lock. No manual OS/signal/listener experiment was run.
