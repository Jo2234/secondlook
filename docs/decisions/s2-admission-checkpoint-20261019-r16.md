## Read-only durable admission lookup

It performs no trimming, case conversion, aliasing or new request-ID validation. Invalid input returns 400; live mode refuses with 503. After validation, `store.assertWritable()` precedes the one synchronous snapshot. A recorded failed/unknown commit owner therefore cannot serve its previous memory as a settled admission. There is no await between this fence and the response snapshot.

The handler is deliberately registered before the fixture API sweep middleware. It completes without calling that middleware, so even an expired buyer cannot make this lookup delete media or commit TTL state. Global app security/body middleware remains in place. The lookup uses only the existing Store API; no new filesystem reads, commits, provider calls, POST, recovery, requeue or durable state are introduced.

The existing durable request record supplies the original ordered job IDs. Exactly one request record, one or two distinct IDs, exactly one matching job per ID, the same request ID/mode and an exact count of jobs bearing that request ID are required. Missing/duplicate/mismatched/extra records fail closed with 503 `admission_record_inconsistent`; jobs are never synthesized or replaced. Only a UUID with neither request nor related jobs returns 404. The success body is the existing `{ mode, jobs }` JobsResponse shape, with each job's current snapshot and the request record's original order. This endpoint reports known admission identity, not completion or provider acceptance certainty.

**An unknown UUID 404 is not proof that an original POST did not commit.** An admission may still be in flight; owner/storage failures require separate reconciliation. A lookup result grants no authority to retry an ambiguous POST, replace its request ID, recover, or spend again. Client unknown-write locking and no automatic POST retry remain required. UI generation and buyer/live paths remain disabled.
