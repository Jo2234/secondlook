## One canonical state publication

The old download path persisted the disclosed file, committed image/job/listing references, and separately sent `downloaded` to settle the attempt and ledger. Cancellation could become terminal between those commits while retaining a published image. A crash could leave references without corresponding success/settlement.

Runner now factors its existing reducer/effect interpretation into a synchronous local `applyEvent`. Both ordinary events and publication use the same `step` and settlement effects. There is no new reducer or alternative deadline/status policy. Terminal events at the Runner boundary are no-ops, so a late abort cannot add history or change a settled outcome. The domain reducer itself is unchanged.

After a fully fulfilled exclusive media write, publication enters the existing serialized Store commit. Inside that callback it checks the composed signal, Store/runtime fences, unique current job, immutable request/job identities, attempt count/number/ledger identity/task/post-send marker, terminal status, correlated unsettled ledger, listing ownership, disabled buyer ownership, image identity and conflicting media/reference IDs/paths. These checks precede all changes. It then applies `downloaded` through the same reducer/effects. Only a reducer-produced `succeeded` with a `spent` effect and matching spent entry publishes the image and job/listing references. Reducer-produced deadline termination commits settlement without an image. An ignored nonterminal transition fails before persistence. No await occurs inside any commit callback.

The single next state includes the generated image/hash, job result ID, listing result ID, succeeded attempt/history and spent ledger/settlement sequence. ## Cancellation order and truthful responses

The synchronous Store callback chooses the logical publication outcome. A cancellation abort that occurs before this callback is checked inside it and refuses publication. A cancel commit that wins serialization leaves a terminal attempt which also refuses publication. If publication chooses its next state first, a later abort during awaited filesystem persistence does not undo that choice. The subsequent cancel commit sees the successfully installed terminal state and returns it unchanged. If persistence fails or is unknown, the Store fence prevents a success/cancel acknowledgement from stale memory.

The route retains controller-abort-before-commit. It now returns every existing terminal job unchanged, including succeeded, cancelled, uncertain, failed and timed_out, instead of appending an ignored cancel history entry. A second terminal cancellation changes neither bytes, history, sequence nor ledger. A response acknowledges the durable job state, not provider deletion, completion of all cleanup, or reversal of units. A success may therefore be returned to a cancel request which arrived after publication was selected. Runner drain still owns the actual operation and cleanup.

## Own unpublished media and conservative retention

Only a fully fulfilled `writeMedia` establishes this operation's exclusive `wx` file ownership and completed file/directory synchronization. A failed/partial write, including EEXIST, is retained at its exact original path. The current Store API cannot prove creation ownership for such a failure; this candidate does not guess or delete it.

After a refused publication or a known durable reducer deadline outcome without publication, cleanup queues a reference check through the same real Store. It checks image IDs/paths, photo IDs/paths, job result IDs, listing original/result IDs and buyer image IDs. It performs no state mutation. Only a successful no-reference proof plus a writable fence permits removal of the exact fully written path. Cleanup neither enumerates nor reconstructs a filename, and never deletes a referenced file. The proof relies on the existing single Store owner, exclusive path creation and the one retained attempt writer; it is not a lease protecting arbitrary external writers or future APIs that can manufacture media references.

Any Store persistence failure, including `not_committed`, fences the owner and prevents this cleanup proof. In particular, rename/directory-sync uncertainty retains the own-media path even when the old memory has no reference. Cleanup errors preserve the publication error as an AggregateError member when distinct and fence unexpected Runner execution; they do not grant retry or hide failed cleanup as success. No automatic reconciliation or orphan sweep is added.
